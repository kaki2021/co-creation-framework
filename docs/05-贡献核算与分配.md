# 贡献核算与分配

贡献核算要回答三个不同的问题：一项工作本身有多大，一项共同成果由谁完成，以及成果后来产生的价值怎样回流。这三个问题不能混成一个数字。

## 三本贡献账

| 账本 | 记录什么 | 何时确认 |
| --- | --- | --- |
| 基础贡献 | 完成任务所投入的有效工作量 | 任务验收后 |
| 成果贡献 | 共同成果内部的创作、决策、修订和反馈份额 | 成果定稿后 |
| 后续价值 | 成果被复用、授权或进入市场后产生的价值 | 复用或结算发生后 |

基础贡献解决“这次做了多少”，成果贡献解决“共同完成的东西怎样分”，后续价值解决“后来产生的收益怎样沿来源关系返回”。

## 一、基础贡献

早期试运行采用下面的计算框架：

$$
C_{task}=\left(\sum_i (T_iW_T+R_iW_R)S_i+H_{comm}+H_{prep}\right)P_{split}
$$

各变量的含义：

- \(T_i\)：第 \(i\) 个模块的技术基准耗时；
- \(R_i\)：第 \(i\) 个模块的创意基准耗时；
- \(W_T, W_R\)：根据任务类型确定的技术和创意权重；
- \(S_i\)：工作量规模系数；
- \(H_{comm}\)：整个任务的沟通耗时；
- \(H_{prep}\)：真实发生的准备耗时；
- \(P_{split}\)：拆分修正系数，用来避免把同一件事拆成很多模块后重复计分。

### 任务类型权重

| 任务类型 | 技术权重 | 创意权重 |
| --- | ---: | ---: |
| 技术开发 | 1.5 | 0.5 |
| 内容创作 | 0.5 | 1.5 |
| 运营推广 | 0.8 | 1.2 |
| 分析研究 | 1.2 | 0.8 |
| 通用任务 | 1.0 | 1.0 |

类型权重只表示这类任务主要依赖什么，不表示某种工作天然高人一等。一个任务只能选一组主权重，不能为了提高分数同时套用多种类型。

### 技术和创意基准

| 技术复杂度 | 基准耗时 | 创意要求 | 基准耗时 |
| --- | ---: | --- | ---: |
| 基础操作 | 1 小时 | 完全按模板 | 1 小时 |
| 标准流程 | 2 小时 | 局部调整 | 2 小时 |
| 使用现有工具 | 3 小时 | 组合已有方法 | 3 小时 |
| 解决具体问题 | 4 小时 | 在既有框架内原创 | 4 小时 |
| 技术研究 | 6 小时 | 突破现有框架 | 6 小时 |
| 系统设计 | 8 小时 | 全新创造 | 8 小时 |

评分时要写出依据：是否需要开发、有没有现成工具、参考案例是否充足、真正的难点是什么。只填等级不写理由，不能进入结算。

### 工作量规模

| 规模 | 系数范围 |
| --- | ---: |
| 微型 | 0.5–0.8 |
| 小型 | 0.8–1.2 |
| 中型 | 1.2–2.0 |
| 大型 | 2.0–3.0 |
| 超大型 | 3.0 以上 |

规模系数必须附带数量、字数、时长、样本或历史记录。能被自动化批量处理的数量增加，不应直接按人工工作量倍增。

### 沟通耗时

试运行材料使用以下公式，避免把每个模块的沟通时间重复相加：

$$
H_{comm}=\max(H_{object})\times0.20+\max(H_{frequency})\times0.35+\max(H_{depth})\times0.35
$$

其中分别取所有模块中“沟通对象、沟通频次、沟通深度”的最高值。项目也可以换成真实工时，但必须在开始前选定一种方法。

### 准备耗时和拆分修正

早期方案把准备耗时固定为 3.5 小时。这个默认值适合一部分中型任务，却可能明显抬高小任务，因此公开框架改为记录真实发生的准备时间。迁移旧记录时可以保留 3.5 小时，但要注明它是旧参数。

拆分修正系数沿用以下试运行区间：

| 模块数 | 修正系数 |
| --- | ---: |
| 1–3 个 | 0.90–1.00 |
| 4–6 个 | 0.75–0.85 |
| 7–10 个 | 0.55–0.70 |
| 10 个以上 | 0.50 |

如果工作确实由多个彼此独立、可以单独验收的模块组成，不应机械惩罚。这个系数主要防止为了增加分数而重复拆分。

## 二、共同成果内部怎样分配

一份文本、设计或方案往往由多人共同完成。试运行材料给出过一组基础角色池：

| 角色 | 基础比例 |
| --- | ---: |
| 决策与定向 | 30% |
| 主要创作 | 40% |
| 关键修订 | 15% |
| 意见反馈 | 10% |
| 润色定稿 | 5% |

角色池内部再按可核对的贡献记录分配。例如修订可以按重大、重要、一般分别记 3、2、1 点；反馈可以按核心、重要、一般分别记 2、1、0.5 点。某人在多个角色中有实际贡献，可以分别获得份额。

早期材料还记录了决策、主笔、修订、反馈的最低比例，以及“S 值上限 2.5”“主笔 20%、决策 10% 的惩罚系数”。但现有资料没有完整说明 S 值和惩罚的触发条件，因此这几项不应直接写进自动结算。等定义、触发条件和申诉方式补齐后再启用。

角色比例也不是所有成果的固定真理。纯技术组件、集体表演或长期维护工作需要重新配置角色池。比例必须在工作开始前公开，不能在看到结果后临时修改。

## 三、成果复用和市场价值怎样回流

基础贡献在验收时确认，不因产品后来卖得好或不好而被抹掉。后续价值另开账本，沿成果关系回流。

### 成果复用

当人物设定、脚本、代码或流程被另一个任务使用时，记录来源成果、使用范围和新成果。复用价值先进入被复用成果的账户，再按照该成果已经确认的内部份额分配。

### 市场回流

产品产生收入后，先扣除事先约定且可核对的直接成本，再按公开规则分到公共积累、当期运营和成果贡献链。市场回流不应只奖励最后一个销售节点，也不应把全部收入按历史贡献无限摊开。

一个简单的表达是：

$$
V_{person}=V_{pool}\times Share_{artifact}\times Share_{person}
$$

其中 \(V_{pool}\) 是本次用于贡献回流的价值池，\(Share_{artifact}\) 是某项成果在本次产品中的份额，\(Share_{person}\) 是个人在该成果中的已确认份额。

## 四、公共积累

共创需要一部分价值留在公共池，用于基础设施、资料维护、风险准备和新成员培养。公共池的比例、用途、审批权限和余额都要可见。它不是无人负责的公款，也不能被项目负责人自行挪用。

## 五、审核和申诉

贡献评估至少经过四步：

1. 执行者提交交付物和事实记录；
2. 验收者确认是否完成，不先讨论人情；
3. 系统或评估人按公开参数计算；
4. 当事人可以对事实、分类或计算提出一次有依据的申诉。

人工复核重点检查重复计分、模糊任务被高估、自动化规模被当成人工规模、验收者利益冲突以及公式计算错误。

无论是否使用人工智能辅助评估，最终依据都必须让人看得懂。模型只能给出建议，不能修改事实、隐藏假设或跳过申诉。
