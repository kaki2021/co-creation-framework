# 规则版本与 Issue 改进

这套框架允许持续修改，但不能让一次结算使用一套临时规则。规则应先公开、再执行；新规则只影响生效后的任务，除非旧记录存在明确的事实或计算错误。

## 一、什么情况适合提出 Issue

- 公式在某类真实任务中明显失真；
- 参数定义不清，导致不同人得出不同结果；
- 两份文档或提示词互相矛盾；
- 缺少一种常见成果类型的内部分配规则；
- 人工智能输出出现重复计分、编造事实或计算错误；
- 审核、回避、申诉或版本记录无法形成闭环；
- 发现隐私、密钥或权限风险。

Issue 不是先争一个人的分数，而是把“现行规则、具体问题、证据和建议修改”放在一起讨论。

## 二、规则改进 Issue 至少写什么

1. 当前使用的规则版本和具体条目；
2. 发生问题的任务类型；
3. 可以公开或脱敏后的真实案例；
4. 现行规则算出的结果；
5. 为什么这个结果不合理；
6. 建议的新规则或参数；
7. 使用同一案例重新计算的结果；
8. 对旧任务、其他成果类型和系统字段的影响。

仓库已经提供[规则改进 Issue 模板](../.github/ISSUE_TEMPLATE/规则改进.md)。只想复核一个算例时，使用[计算案例复核模板](../.github/ISSUE_TEMPLATE/计算案例复核.md)。

## 三、怎样决定是否采用

规则修改先判断影响范围：

- 只影响一个岗位的操作说明，由该岗位和直接上下游确认；
- 影响一种成果类型的分配，由使用该规则的成员评审；
- 影响全平台的贡献、产权、收入或基本权利，由公共治理程序审议。

涉及贡献规则时，至少需要：

- 一名规则维护者检查文字和公式；
- 两名实际使用者用真实案例复算；
- 受影响成员有机会查看和提出异议；
- 利益直接相关者说明关系，必要时回避最终表决。

表决不能只写“同意”或“反对”。每个结论都要说明依据，以及是否需要迁移历史记录。

## 四、版本号怎样变化

规则版本采用“主版本.次版本.修订号”：

- 修订号变化：错别字、链接、例子或不改变结果的说明；
- 次版本变化：增加成果类型、参数或流程，旧数据仍可解释；
- 主版本变化：核心计算、产权或治理逻辑发生不兼容变化。

任务卡必须写明采用的规则版本。提示词版本和配置文件版本应与规则版本对应，不能只改提示词而不改规则说明。

## 五、修改顺序

一次规则修改按下面的顺序完成：

1. Issue 说明问题和证据；
2. 更新规则正文；
3. 更新机器可读参数；
4. 更新对应提示词；
5. 用至少三个历史案例回放；
6. 记录新旧结果差异；
7. 完成人工评审后合并；
8. 在下一批任务启用。

规则永远优先于提示词。提示词只是帮助执行规则的工具；两者冲突时，按已经发布的规则版本处理，并提交 Issue 修正提示词。
