# 平台支撑能力

原演示文稿展示了一张大型关系图，其中既有共创平台的公共能力，也有漫剧生产的具体流程。公有框架只保留前者。剧情分析、人物图片、分镜、配音和视频制作等内容属于产品插件，由具体项目自行建设。

## 公共平台需要支持的四层能力

### 一、团队治理

- 共同规则和制度文件；
- 会议决定及其执行状态；
- 问题、意见、异议和处理结果；
- 成员角色、岗位权限和轮换记录；
- 财务、合同、知识产权和公共资产的必要记录。

团队治理保存的是共同部分。个人联系方式、证件、账号和不相关的私人信息不应进入公共仓库。

### 二、工作推进

- 项目、阶段、任务和事项；
- 前置输入、后置使用者和验收条件；
- 负责人、协作者、时间和状态；
- 风险、阻塞、升级处理和复盘；
- 项目之间的接口和依赖。

平台可以提供统一字段，但不替具体岗位决定怎样完成专业工作。

### 三、知识和成果

- 文档、代码、设计、数据、方法和其他可复用成果；
- 成果的版本、来源、作者和使用范围；
- 原成果、修改版本和派生成果之间的关系；
- 哪些成果属于项目私有，哪些可以公开或跨项目复用；
- 维护者、复查日期和失效状态。

知识库保存可以继续使用的成果，任务平台保存工作如何推进。两者需要连接，但不应混成同一张表。

### 四、贡献和反馈

- 已验收工作的基础贡献；
- 共同成果的内部份额；
- 成果复用、授权和市场回流；
- 用户、成员、质量和运营反馈；
- 参数变更、人工复核和申诉记录。

贡献账使用任务和成果中的事实，不重新创造另一套工作记录。

## 最少需要的数据对象

| 对象 | 最少字段 |
| --- | --- |
| 项目 | 目的、边界、负责人、治理规则、状态 |
| 岗位 | 目的、输入、输出、权限、反馈、升级条件 |
| 任务 | 问题、交付物、执行人、验收人、前后关系、状态 |
| 成果 | 名称、版本、来源、贡献者、权限、复用关系 |
| 决定 | 背景、影响范围、参与者、结果、复查日期 |
| 贡献 | 对应任务或成果、事实依据、参数、结果、异议 |
| 问题 | 现象、影响节点、负责人、处理状态、结果 |
| 结算 | 收入、直接成本、价值池、分配关系、确认状态 |

这些是结构定义，不包含任何项目的真实任务、提案、成员或结算数据。

## 关系图怎样生成

关系图应当来自实际记录：任务引用了什么输入、交付给谁，成果从哪个版本修改而来，产品使用了哪些成果。人工智能可以把这些记录整理成 Mermaid、图数据库或其他可视化形式，但不能根据相似词语自行认定产权和贡献关系。

通用平台应允许每个项目拥有自己的局部关系图，再通过少量公共接口连接。这样既能看到整体影响，也不会要求所有项目使用完全相同的生产流程。

## 自动化和人工智能

适合自动化的工作包括：

- 提醒缺失字段、逾期和依赖变化；
- 汇总已经确认的数据；
- 检查贡献公式和重复关系；
- 生成关系视图和阶段报告；
- 从反馈中提取需要人工处理的问题。

需要人工确认的工作包括：

- 成果是否达到验收标准；
- 证据是否真实、关系是否成立；
- 价值冲突、人员任用和重大规则修改；
- 知识产权、隐私和对外承诺；
- 争议与申诉的最终处理。

## 权限和仓库边界

公有仓库可以保存框架、字段说明、算法、空白模板和公开案例。项目私有库保存受限的创作资料、真实任务、内部决定和未公开成果。成员联系方式、账号、密钥和系统配置只保存在专门的权限系统中，不进入版本库。

一个成员能查看某项工作的状态，不代表可以读取该项目的全部资料。权限应跟随实际职责和协作关系，而不是只分成“管理员”和“普通成员”两档。

## 建设顺序

先用文档和表格跑通岗位、任务、成果、贡献和决定之间的关系。只有当手工维护已经影响工作时，再逐步增加任务平台、知识库、关系图、自动核算和本地模型。平台建设服务于已经确认的组织规则，不能代替团队形成规则。
