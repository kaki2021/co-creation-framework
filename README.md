# 共创协作框架

这里整理的是一套可以反复使用的共创方法：成员怎样发起事情、组成协作关系、独立完成工作、计算贡献、共同作出决定，并在项目变化时及时调整。

当前公开规则版本为 **0.1.0（试运行）**。规则、参数、提示词和填写模板已经配套，可以直接选择一个小项目开始试用，再通过 Issue 提交真实案例和改进建议。

这套框架把共同规则和节点自主放在同一个系统里。公共层负责方向、底线、公共资产和争议处理；具体工作的判断权留给最了解现场的人。

它主要处理四个问题：

- 团队怎样在保持效率的同时，尊重每个人的目标、能力和时间边界；
- 个人怎样在完成工作的过程中成长，并逐步具备独立发起项目的能力；
- 任务、成果、成员和后续收益怎样形成可以追溯的关系；
- 软件和人工智能怎样减少重复劳动，同时保留人的判断、确认和申诉权。

## 先说明三件事

- **去中心化不等于没有中心。** 项目仍然需要共同方向、公共账本和争议处理机制，只是不让一个中心包办所有决定。
- **节点自主不等于各干各的。** 承担者需要理解上游输入，完成自己的调研、分析和判断，再把可用的成果交给下游。
- **贡献值不等于人的价值。** 它只是一种项目内部的记录和分配工具，不能拿来给人分等级，更不能代替信任、判断和协商。

## 最快开始方式

1. 用[任务卡](templates/任务卡.md)写清目标、交付物、验收条件、成果类型和规则版本；
2. 依次使用三段任务贡献值提示词，得到人工智能建议值；
3. 用[任务贡献值评审表](templates/任务贡献值评审表.md)完成人工验收，确认任务总贡献值；
4. 根据成果类型选择内部分配方案。文档型成果直接使用[动态分配规则](docs/14-文档型成果动态分配.md)；
5. 参与者核对事实、比例和利益冲突，完成一次申诉期后确认；
6. 用三到五个已经完成的任务回放，再决定是否调整参数或开发软件。

这里最重要的是规则，不是提示词。提示词只是帮助整理事实、检查计算和减少重复工作；任何人工智能输出都要经过人的确认。

## 提出问题和改进规则

发现公式、参数、提示词或案例有问题时，可以直接创建 GitHub Issue。仓库提供“规则改进”和“计算案例复核”两种模板。请尽量给出脱敏案例、现行结果、新方案和复算结果，这样其他人可以真正验证。

不要在 Issue、文档或代码中提交真实成员资料、未公开作品、会议原文、账号、口令、API 密钥或访问令牌。

## 资料边界

这套文档整理自早期的共创平台设计和试运行材料，只保留可复用的方法。具体产品的剧情资料、生产流程图、任务、提案、会议记录、成员资料、账号信息、后台截图和内部评估结果都不在这个仓库中。

目前它是一套可以试运行的框架，不是不可修改的章程。真正采用时，应先用小项目跑一轮，再根据实际争议修订参数。
